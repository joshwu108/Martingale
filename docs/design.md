## 1. Policy Parameterization Decision

### Background

The centerpiece of T2 is a machine-checked exact rational equality:

> E_{τ~b}[ IS-REINFORCE gradient ] = true on-policy gradient

where every term must be an **exact reduced fraction**.  Floating-point probabilities
are irrational in general and cannot appear on either side of this identity.
The parameterization choice determines where (if anywhere) floats are permitted
to enter the system.

---

### Option A — Direct Rational Simplex Parameterization *(recommended default)*

**Representation.** A policy at state s is a tuple of non-negative rationals
`(p_1, …, p_k)` with `sum = 1` stored as Python `fractions.Fraction` objects.
No parameters outside the simplex are ever needed; the policy *is* the probability
table.

**Gradient ascent.** The REINFORCE gradient w.r.t. the simplex coordinates
(using the standard projected gradient with the simplex constraint handled via
a rational subtraction of the mean) yields exact Fraction updates.  One gradient
step: `p_i ← p_i + α·G·(1_{a=i} − p_i)` for a rational step size α and
rational return G — this keeps every p_i rational and the sum = 1 invariant
is preserved exactly.

**Log-prob gradient (for IS weight denominator).** For a simplex-parameterized
policy, `log π(a|s)` is not a polynomial, but its **gradient w.r.t. the
probability table entries** is:

```
∂ log π(a|s) / ∂ p_i  =  (1_{i=a}) / p_a   − 1/(sum of p)   (= 1/p_a − 1 for i=a, −1 for i≠a … but sum=1)
```

More precisely, REINFORCE uses `∇_θ log π` for a gradient step, not a policy
gradient in the traditional sense — the "parameters" *are* the probability
entries, subject to the simplex constraint.  This is cleanest for T2/T3 and
is what is meant by "the rational simplex gradient."

**Property tests.** Exact rational finite-difference checks: perturb `p_i` by
`ε = Fraction(1, 10**6)` (keeping sum=1 by adjusting another entry),
re-evaluate `log π(a|s)`, and compare the central difference to the analytic
gradient — all in `Fraction` arithmetic.  No floats needed.

**Pros:**
- Probabilities are fractions by construction — zero float contamination.
- IS weights `π_target(a|s) / π_behavior(a|s)` are exact Fraction divisions.
- Gradient ascent preserves rationality with any rational step size.
- Enumeration over trajectories accumulates exact Fraction products.
- Cleanest possible for T2 and T3.

**Cons:**
- The rational simplex policy is *not* a softmax policy, and results do not
  transfer to softmax parameterization (explicitly stated in nonclaims.md).
- "Policy parameters" in the traditional sense are the probability entries
  directly, which some readers may find unusual.
- Simplex projection must be done carefully to avoid the sum drifting from 1
  under repeated updates (exact arithmetic prevents drift but requires care).

**Verdict:** Use for all of T2, T3, T5, T7.

---

### Option B — Float64 Softmax → Integerized Table

**Representation.** Compute softmax in float64 once per revision, multiply by
a large integer denominator (e.g. 10^18), round to integers, normalize exactly.
The resulting integer table *is* the declared policy.

**Pros:**
- Closer to production parameterizations.
- Natural bridge to T4's float-divergence study.

**Cons:**
- Introduces a declared float→rational boundary at policy creation time.
- The "gradient" must be defined w.r.t. the declared table, not the
  underlying float parameters — conceptually awkward.
- The true softmax gradient is then inaccessible for T2/T3 (unless
  we separately track float parameters, muddying the exact-computation claim).
- Policy divergence in T3's revision chain cannot be generated by exact
  gradient ascent in the softmax parameterization without reintroducing floats.

**Verdict:** Use *only* in `campaigns/float_baselines.py` (T4) as the
float defendant — producing policies that are compared against Option A
exact-rational policies.

---

### Option C — Polynomial-Parameterized Policies

**Representation.** Each action probability is a polynomial in a rational
parameter vector with rational coefficients; softmax-like normalization
implemented symbolically.  Gradients of log-prob w.r.t. the polynomial
parameters are exact rationals by the quotient rule.

**Pros:**
- Parameter space is unconstrained; closer to softmax in spirit.
- Gradients are mechanically exact.

**Cons:**
- Substantially more complex to implement correctly (symbolic polynomial
  arithmetic, normalization invariant).
- Trajectory enumeration requires evaluating polynomials at rational points —
  still exact, but slower.
- Offers no scientific advantage over Option A for T2/T3: the identities hold
  for any exact rational policy, not just polynomial ones.
- Unnecessary complexity for the current theses.

**Verdict:** Not adopted; reserved as future extension if a reviewer
demands it.

## 2. Exact Enumeration Semantics

### MDP definition

A rational MDP is a tuple `(S, A, T, R, H, s_0)` where:
- `S` is a finite set of states (integers).
- `A` is a finite set of actions (integers).
- `T : S × A → Δ(S)` — transition distribution, each entry a `Fraction ≥ 0`,
  rows summing to exactly 1.
- `R : S × A × S → Fraction` — exact rational rewards.
- `H` is the horizon (integer).
- `s_0` is the initial state (or a distribution over states as a `dict[int, Fraction]`).

All tables are stored as nested dicts of `fractions.Fraction` objects.
Inf/NaN are rejected loudly at construction time.

### Trajectory

A trajectory of horizon H is a sequence:

```
τ = (s_0, a_0, s_1, r_0,  s_1, a_1, s_2, r_1,  …,  s_{H-1}, a_{H-1}, s_H, r_{H-1})
```

encoded as a tuple of `(state, action, next_state, reward)` steps.

The **exact path probability** under a *per-step* policy assignment
`π_t : S → Δ(A)` (allowing mixed-revision trajectories) is:

```
P(τ) = ∏_{t=0}^{H-1}  π_t(a_t | s_t) · T(s_{t+1} | s_t, a_t)
```

Each factor is a `Fraction`; the product is exact.

### Enumeration engine

The enumeration engine iterates over all `|A|^H` action sequences
(per start state) via a recursive depth-first traversal.  At each step it
multiplies in the exact `π_t(a_t | s_t)` and `T(s_{t+1} | s_t, a_t)` factors.
Terminal nodes accumulate `P(τ) · f(τ)` for any trajectory functional `f`.

**Feasibility guard:** total trajectory count = `|S| · |A|^H` (summed over
all start states) must be verified ≤ 10^7 before any campaign run.

**Mixed-revision support:** `π_t` can be a different policy object at each
time step, enabling exact enumeration for trajectories where the behavior
policy changed mid-episode.

### Expected gradient

The exact on-policy expected gradient is:

```
∇J = Σ_τ  P_π(τ) · G(τ) · Σ_{t=0}^{H-1} ∇_θ log π(a_t | s_t)
```

computed as a finite exact sum of `Fraction` products. Each component
of the gradient vector is a separate `Fraction`.

For IS-REINFORCE under behavior policy `b`:

```
∇̂J_IS = Σ_τ  P_b(τ) · w(τ) · G(τ) · Σ_t ∇_θ log π(a_t | s_t)
```

where `w(τ) = P_π(τ) / P_b(τ)` is the exact IS weight (transition
factors cancel, leaving only the policy probability ratios).

T2's identity asserts: `E_{τ~b}[∇̂J_IS] = ∇J` as an exact `Fraction`
equality, component-by-component, verified by the enumeration engine.

## 3. Ledger Schema

Each **action record** in the ledger contains:

| Field | Type | Description |
|---|---|---|
| `revision_digest` | `str` (hex) | BLAKE2b-256 of the canonical revision bytes |
| `state` | `int` | State at which action was drawn |
| `action` | `int` | Action drawn |
| `behavior_prob_num` | `int` | Numerator of exact behavior probability (reduced) |
| `behavior_prob_den` | `int` | Denominator of exact behavior probability (reduced) |
| `draw_integer` | `int` | Raw draw integer from BLAKE2b uniform sampler |
| `rejection_count` | `int` | Number of rejections in rejection sampling |
| `prev_record_digest` | `str` | BLAKE2b-256 of the previous record's canonical bytes (chain) |
| `env_next_state` | `int` | Observed next state |
| `env_reward_num` | `int` | Numerator of exact reward (reduced) |
| `env_reward_den` | `int` | Denominator of exact reward (reduced) |

Each **trajectory record** links the sequence of action records plus:

| Field | Type | Description |
|---|---|---|
| `actor_id` | `int` | Actor process identifier |
| `episode_id` | `int` | Episode counter within actor |
| `action_records` | `list[ActionRecord]` | Ordered list, each pinning its own revision |
| `terminal_digest` | `str` | BLAKE2b-256 of the final action record |
| `prev_trajectory_digest` | `str` | Hash of prior trajectory in per-actor chain |

### Why draw_integer + rejection_count catches cross-revision forgeries

The checker does not merely re-derive `π(a|s)` for the claimed revision and
check it matches the ledger's `behavior_prob`.  It also re-runs the BLAKE2b
uniform draw with the keyed seed `(seed, actor_id, episode, step)` and
verifies that rejection-sampling with the *full* simplex of the claimed
revision would have produced exactly `action` after `rejection_count`
rejections, consuming `draw_integer` as the first accepted draw.

This catches the subtle forgery class: if action `a` is drawn under revision
`r+1` but the ledger claims revision `r`, and both revisions assign the *same*
probability to `a`, the probability check passes — but the draw-integer check
fails, because the ordering of the full simplex differs between revisions
(different probability masses in different "slots" change which draw integers
map to which actions under rejection sampling).

## 4. Pin-Before-Draw Protocol State Machine

The protocol ensures actors never ledger an action under the wrong revision.

### States per actor episode

```
IDLE
  │  actor requests pin for episode e
  ▼
PINNED(revision=r, episode=e)
  │  actor draws action using only revision r's simplex
  ▼
DREW(revision=r, action=a, draw=d, rejections=k)
  │  actor writes action record to ledger
  ▼
APPENDED(record_digest=h)
  │  actor sends ack to learner
  ▼
IDLE  (next step)
```

### Invariant

> For every action record in the ledger, the revision pinned by the actor
> at the PINNED state equals `record.revision_digest`.

### Learner side

The learner publishes new revisions by appending to the revision store and
broadcasting the new digest.  A broadcast may arrive at an actor in any
state.  The invariant is maintained because:

1. The actor pins a revision *before* drawing (PINNED is entered before DREW).
2. The draw function takes only the pinned revision's simplex as input —
   it is structurally impossible to draw under a different revision.
3. The ledger record is written with the pinned revision digest — which equals
   the revision used for the draw by construction.

### Crash cuts

Cut points (for T5 campaign):
- **pre-pin**: actor crashes before pinning. Recovery: no ledger entry, no
  inconsistency.
- **post-pin-pre-draw**: actor crashes after pinning but before drawing.
  Recovery: pin abandoned, no ledger entry.
- **post-draw-pre-append**: actor crashes after drawing but before ledger write.
  Recovery: draw discarded, no ledger entry.
- **post-append-pre-ack**: actor crashes after ledger write but before ack.
  Recovery: record is in the ledger; learner may not know, but the ledger
  is consistent. On restart, actor resumes from IDLE.
- **learner-publish cut**: learner crashes mid-publish. Recovery: partial
  revision write is never committed (atomic rename).

### Durability protocol

All ledger and revision store writes use:
1. Write to a temp file in the same directory.
2. `fsync` the temp file (`fcntl.fcntl(fd, fcntl.F_FULLFSYNC)` on Darwin).
3. Atomic `os.rename(tmp, target)`.
4. `fsync` the parent directory.

This ensures crash-safety on macOS (where plain `os.fsync` does not guarantee
durable storage).

## 5. Explicit Non-claims (pointer)

See `docs/nonclaims.md` for the full list.  Key non-claims:

- These results apply only to finite, tabular, rational-parameter MDPs.
- No claims about softmax / neural-network policies.
- No function-approximation claims.
- No deep-RL or RLHF-scale claims.
- The BLAKE2b draw is not a security boundary.
- Results are single-host, CPU-only; no distributed-systems claims.
