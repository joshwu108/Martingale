# Draft comment for TRL rollout version discussion

The [rollout-source RFC #5974](https://github.com/huggingface/trl/issues/5974) defines `model_version` on each `RolloutSample` and on each captured turn, but is closed as not planned. The older [weight-sync interface issue #5195](https://github.com/huggingface/trl/issues/5195) is also closed. Live venues checked 2026-10-10:

- [Discussion #5509, Decouple rollout from trainer process — RolloutService protocol](https://github.com/huggingface/trl/discussions/5509): asks how an external rollout service can return completed trajectories with a policy version. **Pick this one** for the token-level provenance proposal below.
- [Issue #6945, AsyncGRPO log-prob mode and importance sampling](https://github.com/huggingface/trl/issues/6945): open discussion of what the engine's reported log-prob means and how the trainer uses it; a narrower place for the `logprobs_mode` point.
- [Issue #6688, GRPO + vLLM numerical safety](https://github.com/huggingface/trl/issues/6688): open discussion of engine/trainer disagreement; a narrower place for the fp32/bf16 observation.

The comment below is a draft for #5509; relate it to that thread's external rollout service when posting.

The `model_version` proposed in #5974 and the ordering of weight sync before generation are useful starting points for diagnosing off-policy updates. Would it be feasible for an external rollout service to preserve a token-aligned provenance record at the rollout boundary? Minimal fields are `(position, token_id, behavior_logprob_bits, revision_digest)` per generated token. A revision binds the trainer step, parent revision, weights digest, tokenizer digest, and sampler config including dtype and `logprobs_mode`; a later score binds the token position, train revision, and trainer log-prob bits. This allows a sequence to span two versions and lets diagnostics separate lag from the lag-0 engine/trainer floor. The [schema](https://github.com/joshwu108/Martingale/blob/main/docs/design.md) is in section 7; it binds what the engine reports, not whether the token was sampled from that distribution.

In one Qwen2.5-0.5B, TRL 1.13/vLLM 0.28 colocated run, our fp32 trainer disagreed with bf16 vLLM by 0.81 and 1.03 nats on generated tokens at steps 4 and 8. We first called it tail noise, then failed sync. A probe found all 494,032,768 vLLM parameter elements equal to the trainer weights cast to bf16 after each sync. With bf16 autocast the lag-0 floor fell to 0.0001–0.03 nats. The sync was correct; our precision configuration was the cause. [Evidence and scope](https://github.com/joshwu108/Martingale/blob/main/docs/findings/2026-10-06-trl-colocate-sync.md). A startup warning for fp32 trainer forward against a bf16 engine could save others this diagnosis.
